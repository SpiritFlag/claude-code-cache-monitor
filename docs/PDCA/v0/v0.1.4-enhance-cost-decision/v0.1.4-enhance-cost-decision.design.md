### 1.2 갈림길 상세

#### D-4 프로젝트 키를 어디서 뽑나

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | `path.relative(ROOT, 파일경로)`의 디렉터리 부분 첫 세그먼트. 없으면 `''` | 실측 아카이브는 세션 jsonl이 `ROOT` 바로 아래에 평평하게 있어 전부 `''` 한 덩어리가 된다. 이 데이터로는 프로젝트가 갈리는 동작을 검증할 수 없다 |
| b | `s.cwd`를 소문자화하고 경로 구분자를 통일해서 쓴다 | 아카이브의 cwd는 `c:\…\CogMoUp-Fishing` 64건 · `C:\…` 17건 · `…\Assets\Games\Fishing` 2건 세 표기다. 대소문자는 정규화로 합쳐지지만 하위 폴더에서 연 세션은 다른 프로젝트가 되어 표본이 쪼개진다 |
| c | a를 쓰되 비면 b로 폴백 | 아카이브에서 a가 항상 `''`이므로 곧바로 b로 떨어져 b의 하위 폴더 문제를 그대로 받는다. 코드는 둘 다 |

**추천**: a. 실사용 `~/.claude/projects/<인코딩된 cwd>/`가 정확히 이 세그먼트이고 CC가 이미 cwd 단위로 폴더를 나눠 두었다. 아카이브가 `''` 하나로 묶이는 것은 손실이 아니라 사실과 일치한다(F-4: 이 아카이브는 프로젝트 하나다).

#### D-8 압축 비용 식

현재 `postCtx = min(total, sysTokens + CAL.summary)` 하나가 두 자리에 쓰인다. `perCallAfter`(압축 후 호출당 캐시 **읽기**)와 `compactionCost`의 **쓰기** 항이다. 실측은 두 값이 다르다: 압축 직후 호출의 컨텍스트 중앙값 87,852인데 그중 캐시 히트로 살아남은 프리픽스가 36,792이고 실제로 다시 쓴 것은 55,885다.

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | 두 자리를 분리한다. 읽기 기준 = 압축 직후 컨텍스트 중앙값(`CAL.postCtx`), 쓰기 기준 = 압축 직후 재작성 중앙값(`CAL.rewrite`), 요약 출력 = `compactMetadata.postTokens` 중앙값(`CAL.summary`) | 재료가 셋이고 표본 수가 각각 다르다(16 · 16 · 19). 재료 하나가 없는 폴더에서 사다리가 셋 다 따로 돈다 |
| b | 재료 둘. `postCtx`를 실측 컨텍스트 중앙값으로 바꿔 읽기·쓰기 두 자리에 그대로 쓰고, 요약 출력만 `postTokens`로 바꾼다 | 압축을 넘어 캐시에 남는 프리픽스 36,792를 "새로 쓴다"고 세어 sonnet 기준 약 $0.147 과대로 남는다. 실측으로 바꾸는 목적의 절반이 남는다 |

**추천**: a. F-6이 압축 호출의 `curCr` 30,921~43,956으로 프리픽스가 압축을 넘어 살아남음을 이미 보였고, 그것을 쓰기로 세는 것이 지금 값이 실측의 4.4~8.7배인 이유 중 하나다. 참고로 sonnet 기준 예상값은 a가 약 $0.676, b가 약 $0.803이다(현재 $1.152).

#### D-9 압축 실측 재료의 집계 단위

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | 폴더 전체 중앙값 하나. 기존 `CAL.summary` · `CAL.regrowth`와 같은 단위를 유지한다 | 여러 프로젝트를 지켜볼 때 압축 크기가 프로젝트마다 다른 것을 뭉갠다. sys는 프로젝트별인데 압축만 폴더 단위라 기준이 둘이 된다 |
| b | sys와 같은 헬퍼로 프로젝트 → 폴더 → 기본값 사다리. 구성 키로는 나누지 않는다(MCP 구성과 압축 크기는 무관) | 표본이 16 · 19건이라 프로젝트로 쪼개면 프로젝트당 한둘로 떨어질 수 있다. 다만 사다리가 상위로 폴백하므로 값이 사라지지는 않는다 |

**추천**: b. sys 사다리에서 이미 프로젝트 버킷을 만드는데 압축만 폴더 단위로 두면 같은 화면의 두 숫자가 다른 단위로 잡힌다. 헬퍼 하나를 필드 이름만 바꿔 재사용하므로 늘어나는 코드는 몇 줄이다.

#### D-10 압축 권유 톤 강화 임계

FR-5의 "임계값을 넘으면 문구 톤을 강화한다". 현재 추천선은 이미 `saving > compactionCost`다.

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | 절대액. 순이득 ≥ $1.00 | 모델 단가에 둔감하다. haiku 세션은 컨텍스트가 아무리 커도 이 선을 넘기 어렵고, opus 세션은 이득이 얇아도 넘는다 |
| b | 비율. 순이득 ≥ 압축 실비 × 3 | 절대액이 푼돈인 작은 세션에서도 배수만 크면 강한 톤이 나온다 |

**추천**: b. 추천선(`saving > compactionCost`, 1배)과 톤 강화선이 같은 척도 위 배수로 놓여 둘의 관계가 코드와 문구에서 그대로 읽히고, 모델 단가가 달라도 뜻이 유지된다. 잠정치이며 조정 관찰 항목을 백로그로 만든다(plan §7 (c)).

### 2.2 인터페이스

```js
// ---------------- server.js ----------------

// D-2. 서버 이름 정규화
const normName = n => String(n).replace(/[^A-Za-z0-9]+/g, '_').replace(/^_+|_+$/g, '');

// D-4. 프로젝트 키: ROOT 상대 경로의 첫 디렉터리 세그먼트. 평평하면 ''
function projectKey(fp) {
  const rel = path.relative(ROOT, path.dirname(fp)).replace(/\\/g, '/');
  if (!rel || rel === '.' || rel.startsWith('..')) return '';
  return rel.split('/')[0];
}

// D-1 · D-3. 파일 상태(files 맵의 f)에 추가
f.cfgNames = new Set();   // 첫 assistant 호출 전까지 모은 서버 이름(정규화 후)

f.compactPost = null;     // 직전 compact_boundary의 compactMetadata.postTokens

// 세션 상태(session()의 초기값)에 추가

s.cfgKey = '';            // 정렬된 f.cfgNames를 '|'로 이은 것. 없으면 ''

s.costByModel = {};       // model -> USD (callCost 누적)
s.compactSamples = [];    // { rewrite, ctx } — 압축 브레이크 시점의 실측. 상한 없음

// D-5. 보정 구조. 기존 CAL.sys/summary/regrowth/n은 folder 층 중앙값으로 계속 채운다
const DEFAULTS = { sys: 45000, summary: 20000, regrowth: 80000, rewrite: 55000, postCtx: 90000 };
const newBucket = () => ({ cold: [], warm: [], summary: [], regrowth: [], rewrite: [], postCtx: [] });
CAL.byKey  = new Map();   // `${projKey}\u0000${cfgKey}` -> bucket   (cold · warm만 채움)

CAL.folder = newBucket(); // 폴더 전체
CAL.rewrite = DEFAULTS.rewrite;  CAL.n.rewrite = 0;   // folder 층 중앙값 (calNote 표시용)
CAL.postCtx = DEFAULTS.postCtx;  CAL.n.postCtx = 0;
CAL.warmSys = null;              CAL.n.warmSys = 0;

CAL.noCfgKey = 0;                // 키를 못 만든 세션 수 (R-3 감지용)

// D-6 · D-7. sys 사다리. ctx 상한은 cold-self에만 적용하지 않는다
// 반환: { sys, source }
function resolveSys(s, ctx)

// 표본을 어디서 채우나
//   f.cfgNames  : case 'attachment'에서 f.cfgFrozen이 false일 때만. 두 type 모두 여기서 모은다
//   f.cfgFrozen : case 'assistant'에서 usage가 있고 <synthetic>이 아닌 첫 레코드를 만나면 true
//   s.cfgKey · s.projKey : 같은 자리(첫 assistant 호출)에서 f로부터 한 번 확정한다
//   s.coldStartCw · s.warmStartTotal : 기존 `if (!s.sysSet)` 블록에서 콜드면 앞을, 웜이면 뒤를 채운다
//   s.compactSamples : 브레이크 판정에서 cause === 'compact'일 때 { rewrite, ctx: total }을 push
//   f.compactPost    : case 'system'의 compact_boundary에서 d.compactMetadata.postTokens (최상위 필드)
//   s.compactions[].summary : 기존 `total - s.sysTokens` 대신 f.compactPost를 쓰고, 없으면 null로 둔다(R-4)
//
// calibrate()가 세 층 버킷을 다시 만든다. 매 스캔마다 CAL.byKey · CAL.byProj · CAL.folder를
// 비우고 모든 세션을 훑어 cold(coldStartCw) · warm(warmStartTotal)을 byKey · byProj · folder 셋 다에,
// summary · regrowth · rewrite · postCtx를 byProj · folder 둘에 넣는다. 그다음 folder 층 중앙값으로
// CAL.sys · CAL.summary · CAL.regrowth · CAL.rewrite · CAL.postCtx · CAL.warmSys와 CAL.n을 채운다.
```

## 4. 열린 질문

1. SC-3의 예시 세션이 사다리와 어긋난다. SC-3은 "`095fb73b`에 추정 표시가 보인다"고 했는데, D-6의 사다리를 이 아카이브에 돌리면 `095fb73b`는 첫 호출 `cr = 28,315`인 웜이고 그 구성 키에 콜드 표본이 4건 있어 `cold-key`(실측(콜드))로 떨어진다. 폴더 전체에 콜드 표본이 7건 있으므로 이 아카이브에서 `default`(추정)로 떨어지는 세션은 하나도 없다. 추정 경로 자체는 SC-1의 `mcp-config-none` 픽스처가 자동 테스트로 덮는다. SC-3의 육안 대상을 실측(콜드)과 실측(웜) 두 세션으로 바꿀 것인가(웜 대상은 키에 콜드 표본이 없는 12건 중 하나, 예: `5f111656` · `90fe7a54`), 아니면 사다리에서 웜 단계를 콜드보다 앞에 두어 SC-3 문장을 살릴 것인가. 앞의 것을 권한다. 뒤의 것은 FR-2가 정한 순서를 뒤집는다. — plan §5 SC-3을 고쳐야 하므로 사용자 판단이 필요하다.
