## 1. 목적

비용 판단에 쓰는 숫자를 추정에서 실측으로 바꾸고, 그 위에 "사고 나면 얼마 · 이어갈까 새로 갈까"를 화면에 올린다. 백로그 다섯 건이 전부 비용 환산 한 뭉치(`price()` · `costAs()` · `riskUsd` · `CAL`)를 지난다. P1-1은 "`DEFAULTS.sys = 45000` 고정값 + 폴더 중앙값 폴백으로 뭉개고 있다 … MCP 구성에 따라 갈린다"고 했고, v0.1.3에서 한 달치 아카이브를 물린 기동 로그가 sys 80,036 · summary 42,753 · regrowth 58,409로 기본값(45,000 · 20,000 · 80,000)과 전부 어긋남을 확인했다. P1-2는 "컴팩트 후 rewrite가 매우 적다 … 실비를 실측으로", P1-3은 "컨텍스트가 클수록 손실이 정비례로 커지는데 그 리스크가 화면에 없다", P1-4는 "재개 버튼을 누르는 순간 비용이 확정되는데, 누르기 전에 판단 근거가 없다", P1-5는 v0.1.3이 셋 중 둘을 닫고 남긴 "costAs()는 세션 전체를 단일 모델로 환산하는데 s.cost는 호출별 실비 누적이라 기준이 다르다"이다. v0.1.1이 브레이크 레코드에 진단 필드를, v0.1.2가 한 달치 아카이브 기준 수치를 남겼기 때문에 이번에는 그 재료로 실비를 뽑을 수 있다. 사용자가 검수에서 밝힌 의도는 "고정값이 아니라 상황에 맞는 값으로 시작하길 원한다, 그 데이터가 있는지가 궁금했다"이고, §3이 그 데이터가 있음을 확인했다. 선후 의존이 있다. P1-1이 `s.sysTokens`를 고치면 P1-4의 "새 세션 비용"과 P1-2의 `postCtx`가 같이 바뀌고, P1-4의 "이어가기를 어느 단가로 환산하나"와 P1-5의 남은 꼬임이 같은 질문이다.

### 2.2 제외

- "작업 단위 경계에서 권유"하는 압축 타이밍 로직 — P1-2 detail의 주의 항목. 이번에는 금액을 실측으로 바꾸는 데서 멈추고 언제 권유할지는 손대지 않는다.
- 모델 전환(상위 모델로 올리기) 카드의 계산 — `escalationAdvice`는 `p.in`만 쓰고 `p.read`를 쓰지 않아 이번 문제와 무관함을 v0.1.3에서 확인했다(F-11). sys 값이 바뀌어 숫자가 따라 바뀌는 것은 전후 대조로만 본다.
- 표시 정합성 묶음 — 습관 순위표의 폴더 단위 렌더, 세션 카드 금액·건수 집합 어긋남, `/api/detail` 40건 절단, `s.breaks` 60건 상한(v0.1.2 report §7). `index.html`을 크게 건드리는 사이클이지만 이 넷은 비용 판단과 무관하다.
- 원인별 색 구분(P2-4), CC `version`을 원인 후보로 쓰는 것 — v0.1.2 report §7의 다른 후보.
- 세션 목록 행에 이어가기 · 새 세션 비용을 넣는 것 — 질문 4 답. 이번에는 TTL 카드 만료 분기(선택 세션)에만 둔다.
- 서브에이전트 호출의 비용 분리 표시 — `s.tok`은 메인·서브를 합산한다. 이번에 모델별로 쪼개더라도 메인·서브는 쪼개지 않는다.
- 구독제 사용량 한도로의 환산 — README "숫자 읽을 때" 첫 줄대로 API 정가 환산을 유지한다.
- 실측값을 디스크 파일에 영속 저장하는 것 — 서버는 기동마다 트랜스크립트 전체를 다시 읽어 집계하므로(F-4) 메모리 맵이면 충분하다. 파일 저장이 필요해지면 그때 별도 사이클.
- 아카이브 원본을 픽스처로 커밋하는 것 — RULE.md 예외 4. 픽스처는 합성한다.
- CI 도입 · `package.json` 추가 — RULE.md 예외 1 · 2.

## 8. 사용자 판단 질문

1. F-2대로 이 아카이브에서는 구성별 키가 sys 값을 갈라 주지 않는다. 그래도 P1-1의 (프로젝트, 구성 키) 구조를 이번에 다 만드는가, 아니면 실측·추정 표시와 프로젝트별 분리까지만 하고 구성 키는 관찰 뒤로 미루는가. — 답(2026-09-05): 다 만든다. 수치 효과는 실사용 폴더에서 관찰한다(R-1). FR-1 · FR-2에 반영.
2. 웜스타트(첫 호출에 `cr > 0`, 재개 마커 없음)의 첫 호출 total을 sys 실측 후보로 칠 것인가. 치면 표본이 7건에서 41건으로 늘지만 값에 공유 프리픽스 히트가 섞여 콜드보다 작게 나온다(중앙값 67,062 vs 80,036). — 답(2026-09-05): 콜드와 웜을 따로 보관하고 폴백 사다리에 웜 칸을 둔다. 사용자의 의도는 "고정값이 아니라 상황에 맞는 값으로 시작하는 것"이고 그 데이터가 있음이 확인됐다. FR-2 · FR-3 · SC-1 · SC-2에 반영.
3. 사고 비용의 식. 현 `riskUsd = ctx × in × 2`를 그대로 쓰는가, 실측대로 공유 프리픽스(압축 호출의 `curCr`, 약 30k)를 빼고 TTL 배수(1.25 · 2)를 반영하는가. 차이는 sonnet 기준 약 $0.12다. — 답(2026-09-05): 그대로 쓴다. 사고 비용은 어림값이다. FR-6에 반영.
4. 이어가기 · 새 세션 · 차액 세 값을 어디에 두는가. TTL 카드 만료 분기(선택 세션)만인가, 세션 목록 행에도 넣는가. — 답(2026-09-05): TTL 카드 만료 분기만. 세션 목록 행은 §2.2 제외. FR-7 · SC-8에 반영.
