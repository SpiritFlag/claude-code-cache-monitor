### 1.2 갈림길 상세

#### D-1 재기록 중복을 무엇을 키로 걸러내는가

Plan FR-4는 "user · attachment · system은 (uuid 기준) 두 번 반영되지 않고, **assistant 레코드의 content 순회도 `message.id` 중복이면 건너뛴다**"를 함께 요구한다. 후반절을 문면대로 구현하면 실측과 충돌한다.

이 문서를 쓰며 아카이브를 재집계한 결과: **같은 `message.id`를 가진 서로 다른 uuid의 assistant 레코드가 9,698개 message.id에 걸쳐 13,071건 있고, 그 13,071건 전부에 content가 있다**(`095fb73b` 예: `msg_011CeQsTmk…`가 thinking 1 + tool_use 2 세 줄로 나뉜다). CC가 한 응답의 thinking · text · tool_use 블록을 별도 줄로 쓰는 정상 기록이다. 현 코드가 `f.seen.has(m.id)` 검사를 content 순회 **뒤에** 둔 것은 이 때문이다 — content는 다 세고 usage만 한 번 센다.

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | uuid 단일 키. `handleRecord` 진입부에서 파일 안에서 이미 본 uuid면 종류 불문 return. `f.seen`(m.id)은 usage 이중 집계 방지 역할로 지금 자리에 그대로 둔다 | Plan FR-4 후반절의 **문면**을 지키지 않는다. 그 목적(재기록된 assistant의 content 이중 집계)은 uuid 스킵이 이미 잡는다 — F-8의 중복 assistant 2,423건은 정의상 uuid가 같다 |
| b | uuid 스킵 + `f.seen.has(m.id)` 가드를 content 순회 앞으로 이동. FR-4 문면 그대로 | 분할 기록 13,071건의 content를 통째로 잃는다. `toolInput` · `toolChars` · `toolNames` · `asks` · `commits` · `assistant` chars가 대폭 줄고, `toolNames`가 비면 `tool_result`의 툴 이름이 전부 `?`가 된다. FR-5 · SC-6("그 밖의 세션은 변경 전과 모든 값이 같다")이 즉시 깨진다 |

**추천**: a. b는 FR-5와 양립하지 않아 plan 안에서 자기모순이고, FR-4 후반절이 노린 결과는 a가 이미 낸다. 사용자가 b를 고르면 FR-5 · SC-6을 plan 세션에서 다시 써야 한다.

#### D-5 `BP_MAX_REWRITE` · `BP_SHRINK_SLACK`을 바꾸는가

| 선택지 | 내용 | 대가 |
|---|---|---|
| a | 두 값 유지. 상수 위 주석의 "잠정치 … P0-4 진단 필드로 한 달 더 보고 조정한다"를 이번 분포(F-10)와 판정 근거로 교체 | 여유가 아래 1,292(18,708 → 20,000)로 얇은 채 남는다. 다음에 rewrite 19,000짜리 breakpoint_shift가 오면 effort_change로 샌다 |
| b | `BP_MAX_REWRITE`를 F-10 여유 안(20,000 ~ 25,140)에서 올린다. `BP_SHRINK_SLACK`은 두 원인을 가르지 못하므로 손대지 않는다 | 표본이 breakpoint_shift 5건뿐이라 어떤 값을 골라도 근거가 5건이다. 위쪽 여유 5,140을 먹는 만큼 effort_change 최소값 25,140에 가까워지고, 그 4건이 다음 데이터에서 조금만 내려오면 오분류가 반대로 생긴다 |

**추천**: a. b가 막는 위험(19,000짜리 shift)은 아직 한 건도 관측되지 않았고, b가 만드는 위험(effort_change 최소 25,140의 오분류)은 135건짜리 모집단을 건드린다. R-5가 "유지도 정당한 결론"이라 적은 대로다.

### 2.2 인터페이스

`server.js` — 파일 상태 필드 교체:

```js
// readFile()의 초기 생성과 truncate 리셋 두 곳에서 markerSeen을 이 이름으로 바꾼다
f.uuidSeen = new Set()   // 파일 안에서 이미 처리한 레코드 uuid
```

`server.js` — `handleRecord` 진입부(현 `if (d.sessionId) …` 앞):

```js
function handleRecord(f, d) {
  // 재기록 구간: CC가 재개하며 이력을 다시 쓴 행은 uuid가 같다. 종류 불문 한 번만 센다.
  if (d.uuid) { if (f.uuidSeen.has(d.uuid)) return; f.uuidSeen.add(d.uuid); }
  if (d.sessionId) f.sessionId = d.sessionId;
  ...
```

`server.js` — `user` case의 재개 마커(현 `if (!f.markerSeen.has(d.uuid)) { … }` 블록 전체를 한 줄로):

```js
if (d.isMeta && RESUME_RE.test(markerText(c))) f.pending.push('resume');
```

`server.js` — assistant case의 `if (f.seen.has(m.id)) return; f.seen.add(m.id);`는 **현 위치(content 순회 뒤) 그대로 둔다**. 옮기지 않는다(D-1a).

`scripts/diag-shrink.js` — usage 줄과 필터:

```js
// usage: node scripts/diag-shrink.js --dir <경로> [--min 2000] [--session <id 접두>] [--cause <원인>]
const SESSION = argv('--session', '');
const CAUSE = argv('--cause', '');
// 세션 루프 첫 줄
if (SESSION && !s.id.startsWith(SESSION)) continue;
// 브레이크 루프의 `if (b.rewrite < MIN) continue;` 다음 줄
if (CAUSE && b.cause !== CAUSE) continue;
```

`test/helper.js` — 반환값:

```js
function runFixture(name) {
  const fp = path.join(__dirname, 'fixtures', name + '.jsonl');
  const { snapshot, sessions, files } = replay(fp);
  const s = [...sessions.values()][0];
  return { s, f: files.get(fp), breaks: s ? s.breaks : [], byCause: s ? s.byCause : {}, snap: snapshot };
}
```

`server.js` — 상수 주석(D-5a를 고른 경우. 값은 그대로):

```js
// 실측 근거(v0.1.2 do §3, 2026-08 아카이브 한 달): breakpoint_shift 5건의 rewrite 최대 18,708 · |rewrite-shrink| 최대 2,753,
// effort_change 135건 중 124건이 |rewrite-shrink| ≤ 3,000이고 rewrite 최소는 25,140.
// 두 원인을 실제로 가르는 것은 MAX_REWRITE 하나이고 여유는 위 5,140 · 아래 1,292다. 표본 5건이라 값은 유지한다.
```

픽스처 필드 규약 — v0.1.1 F-13대로 집계에 쓰는 필드만 남긴다. `type` · `sessionId` · `uuid` · `timestamp` · `effort` · `isMeta` · `isCompactSummary` · `subtype` · `attachment.type` · `message.{id,model,content,usage,stop_reason}`. `lastPrompt` · `cwd` · 홈 경로 문자열을 넣지 않는다(SC-8).
